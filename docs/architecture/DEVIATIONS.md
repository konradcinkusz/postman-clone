# Deviations from architecture-standards

This register records every place where postman-clone departs from the reference architecture
(P1–P15 and the guides it cites), with the reason and the date. A deviation is allowed only when it
is written here first; an undocumented departure is a review finding.

Columns: the principle or guide departed from, what this repository does instead, the reason, and the
date it was recorded.

| Date | Principle or guide | Deviation | Reason |
|---|---|---|---|
| 2026-10-26 | P2 example call `AddDatabaseContext<TContext>(configuration, "mydb", "MyDbInMemory")` | `AddDatabaseContext<TContext>(builder, connectionName)`. The InMemory path names its in-memory database after the connection name; there is no second name argument | The builder carries the configuration, and the second name gave the InMemory path nothing the tests needed. WP01 |
| 2026-10-30 | BLAZOR-WEB-APP §7 "cookie authentication on the host" | A custom authentication handler (`SessionAuthenticationHandler`) reads a cookie that holds only a random session id. The ticket and the token pair stay in `ServerSessionStore` on the server, not in a Data Protection cookie ticket | The cookie must carry nothing but a random id (ADR-0005). The cookie middleware's ticket is an encrypted envelope around the principal, not an id. ADR-0013. WP12 |
| 2026-10-31 | Reference checklist §3, item 14: outbound `HttpClient`s carry the standard resilience handler (P2) | The sender (`ExecutionService/Sending/Execution/RequestExecutor.cs`) builds its own `HttpClient` over `SocketsHttpHandler` with no resilience handler, so it never retries. Its own limits (timeout, redirect cap, read cap, SSRF guard) apply instead. | A user's request is not resent silently: a retried POST would send a second request to a third party. ADR-0014 does not record this yet (OI-08). WP14. |
| 2026-10-31 | Reference checklist §3, item 18 and P12: built by a tag-driven workflow with path-based change detection | CI runs on pull requests to `main` (`pr-validation.yml`, `secret-scan.yml`). `detect-changes` finds which inputs exist; it does not filter by path. No tag triggers exist, and the scan workflow says so. | Deployment is out of scope and tags are forbidden for this build (ADR-0007, PROTOCOL §3). WP00, WP27. |
| 2026-10-31 | Reference checklist §3, item 13 and P7: one `fly.toml`; Fly.io as the deployment target | No platform configuration exists. The Dockerfiles are reviewed and built by CI but never pushed. | ADR-0007: deployment is out of scope; the owner decides a target. `docs/OPERATIONS.md` §8 lists what would be needed. |
| 2026-10-31 | P1: the AppHost is the composition root for local development | A second composition path runs the same services as processes: `scripts/run-local-stack.sh`. Its `Auth__*`, `ConnectionStrings__*` and key wiring duplicates parts of `src/PostmanClone.AppHost/Resources/`, with no check that they agree (OI-14). | Sessions and developers without Docker cannot run the AppHost (ADR-0010, plan §6). REPO-BASELINE §8 asks for one authoritative place per variable; `docs/OPERATIONS.md` §1 names it. WP03, WP26. |
| 2026-10-31 | Reference checklist, E2E: the browser journeys run against the no-Docker estate, and the sender's loopback switch is set for them | The local stack sets `Execution:Ssrf:AllowLoopback` when `E2E_SENDER_LOOPBACK=1` (the service refuses it in Production, so that stack runs as Development). The default refuses loopback, and a second run proves the refusal. The switch is local and test-only; the AppHost never sets it. | A journey that sends to a target needs a reachable target, and the default guard refuses every local address by design. The alternative was a second product build. ADR-0018 |
