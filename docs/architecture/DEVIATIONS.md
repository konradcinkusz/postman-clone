# Deviations from architecture-standards

This register records every place where postman-clone departs from the reference architecture
(P1–P15 and the guides it cites), with the reason and the date. A deviation is allowed only when it
is written here first; an undocumented departure is a review finding.

Columns: the principle or guide departed from, what this repository does instead, the reason, and the
date it was recorded.

| Date | Principle or guide | Deviation | Reason |
|---|---|---|---|
| 2026-10-26 | P2 example call `AddDatabaseContext<TContext>(configuration, "mydb", "MyDbInMemory")` | `AddDatabaseContext<TContext>(builder, connectionName)`. The InMemory path names its in-memory database after the connection name; there is no second name argument | The builder carries the configuration, and the second name gave the InMemory path nothing the tests needed. WP01 |
| 2026-10-30 | BLAZOR-WEB-APP §7 "cookie authentication on the host" | A custom authentication handler (`SessionAuthenticationHandler`) reads a cookie that holds only a random session id. The ticket and the token pair stay in `ServerSessionStore` on the server, not in a Data Protection cookie ticket | The cookie must carry nothing but a random id (ADR-0005). The cookie middleware's ticket is an encrypted envelope around the principal, not an id. ADR-0013. WP12 |
| 2026-10-31 | Reference checklist §3, item 14: outbound `HttpClient`s carry the standard resilience handler (P2) | The sender (`ExecutionService/Sending/Execution/RequestExecutor.cs`) builds its own `HttpClient` over `SocketsHttpHandler` with no resilience handler, so it never retries. Its own limits (timeout, redirect cap, read cap, SSRF guard) apply instead. | A user's request is not resent silently: a retried POST would send a second request to a third party. ADR-0014 does not record this yet (OI-08). WP14. |
| 2026-10-31 | Reference checklist §3, item 18 and P12: built by a tag-driven workflow with path-based change detection | CI runs on pull requests to `main` (`pr-validation.yml`, `secret-scan.yml`). `detect-changes` finds which inputs exist; it does not filter by path. No tag triggers exist, and the scan workflow says so. | Deployment is out of scope and tags are forbidden for this build (ADR-0007, PROTOCOL §3). WP00, WP27. |
| 2026-10-31 | Reference checklist §3, item 13 and P7: one `fly.toml`; Fly.io as the deployment target | No platform configuration exists. The Dockerfiles are reviewed and built by CI but never pushed. | ADR-0007: deployment is out of scope; the owner decides a target. `docs/OPERATIONS.md` §8 lists what would be needed. |
| 2026-10-31 | P1: the AppHost is the composition root for local development | A second composition path runs the same services as processes: `scripts/run-local-stack.sh`. Its `Auth__*`, `ConnectionStrings__*` and key wiring duplicates parts of `src/PostmanClone.AppHost/Resources/`, with no check that they agree (OI-14). | Sessions and developers without Docker cannot run the AppHost (ADR-0010, plan §6). REPO-BASELINE §8 asks for one authoritative place per variable; `docs/OPERATIONS.md` §1 names it. WP03, WP26. |
| 2026-10-31 | Reference checklist, E2E: the browser journeys run against the no-Docker estate, and the sender's loopback switch is set for them | The local stack sets `Execution:Ssrf:AllowLoopback` when `E2E_SENDER_LOOPBACK=1` (the service refuses it in Production, so that stack runs as Development). The default refuses loopback, and a second run proves the refusal. The switch is local and test-only; the AppHost never sets it. | A journey that sends to a target needs a reachable target, and the default guard refuses every local address by design. The alternative was a second product build. ADR-0018 |
| 2026-10-31 | P15: every outbound call is traced | The sender's outbound requests are not traced (`ServiceDefaults/Telemetry/OutboundTelemetry.cs`). Their URL is the user's target, and a variable can put a secret in its path. The other clients keep their spans. | The span would carry user data, and the exporter, when set, would send it off the service (SECURITY_REVIEW SR-02, ADR-0019 §1). WP28 |
| 2026-11-01 | P12 and FLY-IO-DEPLOYMENT §10: a tag-driven pipeline (`push tag v*`) builds and deploys in dependency order | Planned (WP33): `.github/workflows/flyio.yml` has `workflow_dispatch` as its only trigger, with an input that selects the app. The order of the jobs is kept (data, then auth, then services, then the Web). `scripts/check-flyio-trigger.sh` fails on any other trigger. No tags are used for deployment | The owner decided that deployment runs only by hand, and no tag or push may start one (ADR-0026 Decision 10). A tag is one accidental `git tag` away from a deployment. ADR-0029 |
| 2026-11-01 | P6: one container per service, built from a multi-stage Dockerfile | Planned (WP30): the local agent (`src/PostmanClone.Agent`) is not a service and has no container. It ships as a .NET global tool and as single-file binaries for three platforms, built by CI as workflow artifacts and never pushed | The agent runs on the user's computer, where a container would not reach the user's localhost or LAN. ADR-0026 Decision 5 and 6 |
| 2026-11-01 | P2: a shared kernel, not a shared domain; the kernel holds no domain types | Planned (WP30): the sending pipeline (assembler, executor, masking, caps) moves to a second shared library, `src/PostmanClone.Sending`, referenced by ExecutionService and by the agent. It is shared code, not kernel code, and it holds no entities or database types. The SSRF guard stays in ExecutionService and is injected | Both senders must apply the same masking and caps to be the same product (ADR-0026 Decision 1 and 6). A copy in each would drift, and the masking is a security control. The kernel's size limit does not change |
| 2026-11-01 | Reference checklist §3, item 14: outbound `HttpClient`s carry the standard resilience handler | Planned (WP30): the agent's sender builds its own `HttpClient` without the resilience handler, as the ExecutionService sender does (the row of 2026-10-31) | A user's request is not resent silently; a retried POST would send a second request to a third party. The agent's limits are the same as the server's (ADR-0014, ADR-0026 Decision 6) |
| 2026-11-01 | ADR-0009 and AGENTS.md "Web": no JavaScript interop and no JavaScript library | Planned (WP31): the Web loads exactly one hand-written script, `wwwroot/agent-client.js`, with no library, and calls it through `IJSRuntime`. The script talks to the local agent on `127.0.0.1` and posts the masked result to the Web's BFF. `script-src 'self'` and the rest of the CSP are unchanged; `connect-src` gains the two agent origins | A server-rendered page cannot reach the user's `127.0.0.1` without script, and a form post cannot read the answer. The exception is one file, tested for being the only script. ADR-0028 |
| 2026-11-01 | FLY-IO-DEPLOYMENT §6 (an OIDC or JWT authority is reached at its public URL) and OPERATIONS §2 (`Auth__RequireHttpsMetadata` stays `true` outside the loopback stack) | Implemented (WP33): the four services and the Web read authservice's discovery document and JWKS at `http://postmanclone-authservice.flycast` with `Auth__RequireHttpsMetadata=false` (`flyio/*.fly.toml`). authservice has no public listener: the owner's topology makes only the Web public. | Traffic stays on Fly's WireGuard-encrypted 6PN, and the internal listeners serve no certificate. The issuer is the constant `PostmanClone`, not the URL, so no token stamps the address. Residual: a peer in the same Fly organisation could serve a forged JWKS. Revisit when authservice is served over HTTPS (internally or publicly). ADR-0029. |
